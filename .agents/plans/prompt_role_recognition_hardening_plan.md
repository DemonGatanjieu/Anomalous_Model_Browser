# 工作流配方：提示词正负角色识别加固计划

状态：规划完成，尚未实施  
日期：2026-08-08  
范围：工作流配方、参数笔记本、节点助手共用的提示词角色识别链路。

## 目标

把“尽量猜出正面/负面”改为“有证据才标注”。系统不必识别所有第三方节点，但绝不能把不确定的提示词错误标为正面或负面。

可见标签只允许以下状态：

| 状态 | 含义 | UI 文案 |
| --- | --- | --- |
| `positive` | 有可靠图结构证据进入正面 conditioning | 正面 |
| `negative` | 有可靠图结构证据进入负面 conditioning | 负面 |
| `both` | 同一文本节点确实同时供应正面和负面路径 | 正面 / 负面共用 |
| `unknown` | 无法从已知结构证明角色 | 提示词角色未确定 |
| `conflict` | 来源、缓存或手动标注彼此矛盾 | 提示词角色冲突 |

`unknown` 和 `conflict` 都不得采用绿色“正面”样式，更不得作为正面提示词参与摘要、对比或节点助手推荐。

## 已知事实与当前缺口

当前保存的新配方会在 `metadata.nodes[].role` 中写入角色；旧配方没有这项数据时，后端已增加“完整提示词文本与 `promptPositive` / `promptNegative` 精确且唯一匹配”的兼容恢复。这修复了旧配方被节点助手一律展示为正面的实际问题。

但现有策略仍不能保证完美：

- 图分析只覆盖部分 CLIP 文本编码类型和部分采样器入口。
- 同一角色存在多个输入或分支时，不能只读取第一条连线。
- 节点摘要有数量上限；角色分析不应因此遗漏工作流深处的节点。
- 同一文本节点同时接到正负路径时，不能用 `if/else` 强行归为正面。
- 不认识的第三方节点不能靠名称、文本内容或“默认正面”猜测。
- 基于旧字段的文本匹配只能作为兼容证据；相同文本同时出现在正负提示词时必须判为不确定。

## 数据与兼容性原则

1. `recipe.workflow` 的完整原始工作流是事实来源；`params`、`metadata` 是可重建的派生数据。
2. 角色分析必须独立于详情页的摘要数量上限，对完整工作流运行。
3. 新格式保存结构化证据，同时保留旧版 `role` 字段供旧 UI 读取。
4. 缺少足够证据时返回 `unknown`，不回退成 `positive`。
5. 不用提示词内容、语言或“看起来像负面词”来判断角色；这些只能用于展示，不能作为语义证据。

建议的新字段（保存于配方元数据，字段名可在实现时微调）：

```json
{
  "prompt_roles": {
    "7": {
      "state": "negative",
      "confidence": "high",
      "evidence": [
        {
          "source": "topology",
          "consumer_node_id": "3",
          "consumer_input": "negative",
          "path": ["7", "3"]
        }
      ]
    }
  }
}
```

为手动修正预留稳定节点引用：节点 ID 加上类型、文本输入索引和局部连接特征。只使用节点 ID 会在导入、复制或重排后失效。

## 实施阶段

### 1. 先冻结行为样本

在改解析器前，为官方节点、现有配方、旧版配方和第三方节点建立最小工作流 fixture。每份 fixture 明确期望状态与证据，不以当前实现输出反推期望。

### 2. 重写为完整图的角色传播器

在 `web/modules/recipe_parser.js` 中建立独立的角色分析函数。

- 构建全部入边、出边和输入槽位，不依赖仅供展示的节点摘要。
- 从所有已知采样/guider 的 `positive`、`negative`、`uncond` 等语义输入出发，保留每一条连接。
- 逆向遍历上游 conditioning 链路；处理分支、合并、复用、循环保护与合理的图规模上限。
- 每条路径累积来源、入口名、节点 ID 和路径，最终按节点聚合为 `positive`、`negative`、`both`、`unknown` 或 `conflict`。
- 将“文本产生节点识别”和“角色路径传播”分开；文本节点不能因为类型名包含 CLIP 就自动获得正面角色。

### 3. 节点语义注册表

新增小型、可审计的注册表，而不是散落的正则与硬编码。

- 内置官方 ComfyUI 节点：`CLIPTextEncode`、采样器、Guider、conditioning 合并/传递节点等。
- 注册表描述语义输入、语义输出、可传递接口以及是否会合并 conditioning。
- 第三方节点只有在注册了明确签名后才参与传播；未知节点终止该路径并产生 `unknown` 证据。
- 注册表可由第三方扩展模块追加，但不能因节点显示名模糊匹配而改变角色。

### 4. 旧数据与 API 兼容层

在 `api/parameters.py` 和配方读取链路中规定优先级：

1. 新格式的图证据与状态；
2. 旧 `metadata.nodes[].role`（标记为缓存/旧来源）；
3. `promptPositive` / `promptNegative` 的完整值、唯一匹配恢复；
4. `unknown`。

若多个来源相互矛盾，返回 `conflict` 并把来源一并交给前端，不静默覆盖。旧格式的兼容恢复必须继续要求“精确、完整、唯一”，不得使用子串匹配或文本相似度。

### 5. UI 与节点助手表现

涉及 `ui_recipe_detail.js`、`ui_parameters.js`、`ui_doctor.js` 及本地化文案。

- `unknown` 显示中性标签“角色未确定”，可展开查看“未找到已知的正负 conditioning 路径”。
- `both` 显示双标签，并在详情中说明该文本被两条路径共用。
- `conflict` 显示警告标签和证据摘要，提供“以当前画布重新分析”与后续手动修正入口。
- 节点助手不得把缺失角色字段的 `CLIPTextEncode` 默认渲染为正面。
- 详情页、参数笔记本、节点助手必须使用同一份角色状态与本地化名称，避免一处为正面、另一处为负面。

### 6. 手动修正（后续小版本）

当第三方节点不在注册表中时，允许用户将提示词标为正面、负面或忽略。修正保存为配方局部元数据，不写入模型数据；应用后仍展示“手动标注”来源。第一阶段即使不交付编辑 UI，也要保留字段与 API 扩展位。

## 测试矩阵

- 官方 `KSampler`、`KSamplerAdvanced`、自定义采样器/Guider 的正负入口。
- 两个以上正面或负面分支、conditioning 合并和中间传递节点。
- 一个文本编码节点同时连接正负入口，期望 `both`。
- 同一节点存在矛盾缓存与图结构证据，期望 `conflict`。
- 两个不同文本节点正负内容完全相同，旧数据恢复必须返回 `unknown`，不得根据文本猜测。
- 旧配方只有 `promptPositive` / `promptNegative` 时的唯一精确恢复。
- 已注册的第三方节点、未注册的透明/不透明第三方节点。
- 超过详情摘要上限的大工作流，工作流末端文本节点仍能正确分析。
- 保存配方、导入配方、参数笔记本读取、节点助手卡片三处输出一致。

除单元测试外，使用实际导出的工作流 fixture 做端到端回归：保存配方后重新打开、导入旧配方、打开节点助手、切换参数笔记，分别核对标签与证据说明。

## 验收标准

1. 不认识的节点不再被默认标为正面。
2. 每个非 `unknown` 状态都能在调试数据或详情中追溯到至少一条结构化证据。
3. 角色分析覆盖所有相关连线，而不是每类输入只取一条。
4. 新旧配方都不会把已验证负面提示词展示成正面。
5. 同一配方在详情页、参数笔记本和节点助手显示完全一致。

## 测试发布建议

当前公开标签最高为 `v1.4.3`，而 `1.5.0` 已存在但未采用 `v` 前缀。若本轮功能仍在快速迭代，建议先发布 GitHub **预发布**而非稳定版：

- 若它是既定 1.5 系列的首次公开测试，使用 `v1.5.1-beta.1`；
- 若你认为工作流配方、参数笔记本和节点助手构成更大的次版本升级，使用 `v1.6.0-beta.1`；
- 仅在功能冻结、关键回归清单通过后才改为 `v1.5.1` 或 `v1.6.0` 正式版。

预发布说明应清楚写明“工作流配方、参数笔记本、节点助手联动为测试功能”，并列出已知限制：未注册的第三方 conditioning 节点会显示“角色未确定”，这是保守设计，不代表提示词无效。发布前至少在干净的 ComfyUI 环境验证：打开/关闭面板、保存与导入配方、打开到新画布、追加到画布、参数笔记应用、模型匹配、旧配方提示词角色恢复。

本计划不修改面向用户的 `CHANGELOG.md`；确认准备发布时，再单独整理用户可读的更新说明。
